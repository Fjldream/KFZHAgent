## 1. 已实现的语义

| 事件 | 实际含义 | 原子边界 / 幂等 |
|---|---|---|
| RUN_ACTION_ACCEPTED / AGENT_RUN | 用户消息、蓝图确认、原生审批或 retry 已受理，不是执行成功 | RunStore 会话锁内，消息/Run/预算/排队事件同一事务；原 clientRequestId 重放直接返回，不重写审计 |
| PLAN_CONFIRMED、PLAN_REVISED、PLAN_CANCELLED / AGENT_RUN | 对应 approve/revise/cancel 决定已被真实 approval 节点消费；不代表后续编译、改稿或交付成功 | approval-decision 节点 memo 与审计在同一 Run 行锁事务保存，稳定审计 id，每 Run 只记一次 |
| BUILD_START / BUILD_JOB | 实际构建作业已入队并绑定当前 Run，不是 worker 已完成构建 | 既有 run-control 锁、有效 owner/fence/租约检查后，job/Run 绑定/审计同事务 |
| BUILD_RESULT / BUILD_JOB | 实际提交的终态：SUCCEEDED 或 FAILED；取消为 FAILED + terminalReason=CANCELLED | completeBuild 的 job/workspace 权威锁和提交事务；排队作业被控制端直接取消时在取消事务记录，不依赖 worker 再来领取 |

原生审批 cancel 后真正关闭 ChangeRequest、消费 interrupt 的后续节点仍保持原有执行逻辑。PLAN_CANCELLED 的 phase 明确是 `approval_consumed`：如果决定后进程中断，不能据此宣称 ChangeRequest 已关闭、工程已撤销或构建已取消，应查看 Run/checkpoint/job 的实际状态。

蓝图受理日志绑定服务器发出的 `blueprintRevision`、`blueprintHash`、`expectedRunId`；原生审批记录原 `planHash`、动作和 `expectedRunId`。关联字段来自已验证请求及持久 Run，不用图中残留的旧 userId 作审批人。构建的 actorUserId 表示 Run 的请求人（`actorRole=requester`），不是伪称后台 worker 是人类执行者；取消发起人仍在既有 RUN_CANCEL_REQUESTED/RUN_CANCELLED 日志中。

最终复核另补真实数据库红测：用户 B 停止用户 A 发起的运行，worker 在进入/恢复审批时自动补 native cancel，旧实现把操作者记成 A。现从原 Run 的 RUN_CANCEL_REQUESTED 审计取经认证的停止发起人，传给取消后继，受理及 PLAN_CANCELLED 均归属 B。缺少原停止审计/actor 时明确 CANCEL_REQUEST_ACTOR_MISSING，不猜原请求人；保持原等待屏障，由获准用户再次显式取消或维护者处置，不能手填日志伪造身份。审计保留策略必须覆盖这种在途依赖。

只保存关联 ID、动作、hash、版本与实际状态；不保存需求正文、原图、模型隐藏思维、完整提示词、私有 storage key/package URL 或凭据。没有为旧的无 Run 作业补造历史审计；已经终态的旧 job 重放也不回填“刚刚完成”。

## 2. 恢复与租约修复

1. RunStepStore 原先在等行锁之前读取 JS 时间。红测让真实 PostgreSQL 会话等待行锁，待租约自然过期再释放；旧实现仍成功保存。现拿到权威行锁后再读 `clock_timestamp()::timestamp`，与 Run 租约的 timestamp 口径一致。旧 fence、过期租约和取消中的审批不写决定/缓存。
2. approval 节点新增 `approval-decision` memo，首次 interrupt 抛出时没有成功输出，不写消费日志；实际消费有效 resume 后才原子保存输出和审计。审计失败会回滚节点输出，不能留下“缓存说完成，日志却丢失”。
3. 故障测试在真实节点 memo 提交之后、图 checkpoint 完成之前注入中断。数据库中已有决定和审计，但原 native interrupt 仍可见；旧 handler 会再次停在 WAITING_APPROVAL。现只重放**当前 Run 已受理且 planHash 精确匹配的原决定**，复用其 memo，不让用户再点一次。
4. 新增内部 `approvalDecisionRunId` 标记。决定已被该 Run 消费后，新审批即使改稿 hash 未变化，也不能复用上一决定。红测复现同 hash 改稿被重复执行而失败；修复后确实再次 WAITING_APPROVAL，随后由新的 cancel Run 消费，审批屏障没有绕过。

这不是人工推断批准，也不在恢复时构造新的用户授权。未知 hash/不属于当前 Run/已消费后产生的新 interrupt 继续等待；原生动作、receipt、基线、签名计划、制品归属保护未放宽。

## 3. 版本与升级

执行配方更新为 **run-plan@5**，使旧的整图输出 hash 失效，并在配置快照中冻结新协议。`run-plan@4` 队列报告和前批 flags 报告仍是历史状态，不应将其作为新 worker 的兼容承诺。

升级顺序：用 §1.1 operations 的 flags/名单停新受理，**先保留旧版 worker 排空旧协议活跃 Run/审批/构建**，确认没有旧版本任务后，再整体切换匹配的 Web/API/agent-worker/build-worker。新 worker 遇到带未知冻结协议的 Run 会在读缓存前以 RUN_CONFIG_VERSION_MISMATCH 拒绝，不会擅自迁移旧批准。旧 null 配置行仍不自动回填，不等于能自动迁移任意历史 checkpoint。

本批未修改实际 `.env`、开启真实租户、重启常驻服务、迁移业务数据库或自动部署。准入默认关闭；启用说明仍见 `agent-runs-operations.md` §1.1。预算和视觉 flags 保持关闭。
