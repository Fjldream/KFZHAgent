# KF 3.6 冗余批量 APP 启停设计

> 日期：2026-09-08
> 状态：设计已确认
> 范围：节点冗余首次生效和节点切换；运维中心、运维代理、冗余任务前端

## 1. 目标与边界

冗余首次生效和节点切换的 APP 阶段不再由中心逐个下发命令。中心针对一个节点的一个阶段只下发一条批量命令，携带该阶段全部受管 APP ID；代理在受控并发下执行，并一次返回完整的逐 APP 结果。

本期只覆盖：

- 首次生效：停止失活节点 APP、启动激活节点 APP。
- 节点切换：停止源激活节点 APP、启动目标节点 APP。
- 冗余任务抽屉中的整批进度及逐 APP 结果。

本期不修改：

- 普通 APP 管理页面、批量接口或多选操作。
- 冗余停用和在线 APP 成员维护。
- 批量部署、重启、撤销部署或删除。
- 角色同步协议；角色确认仍只处理角色和 revision。
- SQLite 表结构和 npm 依赖。

## 2. 命令数量与执行并发

“批量命令数量”和“代理执行并发”是两个独立概念：

- 中心把当前节点、当前阶段的全部 APP ID 放进一条命令。
- 代理内部按动作限制同时执行数量，超过限制的 APP 在本次命令内部等待补位。

| 动作 | 单条命令内容 | 代理最大并发 |
|---|---|---:|
| START | 当前 APP 阶段全部 APP ID | 4 |
| STOP | 当前 APP 阶段全部 APP ID | 8 |

启动涉及进程拉起和初始化，因此限制为 4；停止路径较轻，限制为 8。不能无上限并发，也不能使用 `pm2 stop all`，以免影响节点上不属于当前冗余配置的 APP。

并发数由代理代码固定控制，中心和前端不能传入任意并发值。

## 3. 命令与结果契约

### 3.1 中心下发

沿用现有批量枚举：

- `NODE_DEPLOYCOMMAND_BATCHSTART`
- `NODE_DEPLOYCOMMAND_BATCHSTOP`

```json
{
  "cmdId": "command-uuid",
  "cmdType": "NODE_DEPLOYCOMMAND_BATCHSTOP",
  "nodeId": "node-uuid",
  "tenantId": "tenant-uuid",
  "user": "admin",
  "appId": ["app-1", "app-2", "app-3"],
  "internalRedundancy": true,
  "redundancyId": "redundancy-uuid",
  "revision": 12,
  "operationTaskId": "task-uuid"
}
```

一条命令只允许包含同一节点、同一冗余配置、同一阶段的 APP。

### 3.2 代理返回

代理执行所有已通过整批校验的项目后，一次上传结果：

```json
{
  "cmdId": "command-uuid",
  "cmdResults": [
    {
      "appId": "app-1",
      "cmdStatus": 2,
      "message": "succeed"
    },
    {
      "appId": "app-2",
      "cmdStatus": 3,
      "message": "pm2 stop failed"
    }
  ]
}
```

约束：

- `2` 表示代理操作调用成功，`3` 表示代理明确失败。
- 返回结果顺序必须与请求 APP ID 顺序一致，与实际完成顺序无关。
- 每个请求 APP ID 必须且只能出现一次。
- 缺项、重复、未知 APP ID 或非数组结果均属于协议异常，不能判为整批成功。
- 一个 APP 失败不取消同批其他已通过校验的 APP。
- 任一 APP 失败时总体命令为失败，但中心必须保留全部子结果。

## 4. 运维代理执行

新增一个纯批量执行器，输入 APP ID、单 APP 动作函数和并发上限。执行器预分配结果数组，通过 worker 获取下一个索引执行，捕获单项返回失败或异常，并按原索引写回结果。

- 批量 START 调用现有 `AppStart(appId)`，并发上限 4。
- 批量 STOP 调用现有 `AppStop(appId)`，并发上限 8。

因此 PM2 工程和按端口控制的非 PM2 工程继续走原有单 APP 分支，不另建第二套进程控制逻辑。

执行前，现有冗余 Guard 必须一次校验全部 APP ID。任一 APP 的冗余 ID、节点角色、revision 或归属不匹配时，整批执行零项，并为全部请求 APP 返回失败子结果。

## 5. 运维中心编排

### 5.1 首次生效

```text
一条批量 STOP：失活节点全部受管 APP
        ↓ 命令结果完整且实际状态全部为停止
同步两端角色和 revision
        ↓ 不执行任何 APP 命令
一条批量 START：激活节点全部受管 APP
        ↓ 命令结果完整且实际状态全部为运行
任务成功
```

### 5.2 节点切换

```text
一条批量 STOP：源激活节点全部受管 APP
        ↓ 命令结果完整且实际状态全部为停止
持久化新角色并同步两端角色和 revision
        ↓ 不执行任何 APP 命令
一条批量 START：目标节点全部受管 APP
        ↓ 命令结果完整且实际状态全部为运行
任务成功
```

源节点离线的强制切换继续跳过源节点 APP 停止和源角色确认，不创建无法下发的 STOP 批量命令。

### 5.3 实际状态确认

代理结果只表示命令调用结果。中心仍从现有节点/APP 状态管理读取实际状态：

- START 期望 `running = true`。
- STOP 期望 `running = false`。

同一阶段使用共享截止时间：START 120 秒，STOP 60 秒；不按 APP 数量累加。代理结果成功的 APP 进入 `OBSERVING`，实际状态达到目标后才进入 `SUCCEEDED`。

### 5.4 失败语义

- 角色变更前，STOP 中任一 `FAILED`、`UNKNOWN` 或实际状态未确认，任务失败且不修改角色。
- 角色变更后，START 中任一失败或未确认，保留新角色，任务失败，不回滚，也不停止已经启动成功的目标 APP。
- 整条命令超时、子结果缺失或实际状态确认超时显示为 `UNKNOWN`，不能伪造成代理明确失败。

## 6. 冗余任务记录与前端

中心必须在下发批量命令前，为本阶段全部 APP 创建 SQLite 步骤记录。现有字段足够使用，不迁移数据库：

- `command_status`：`PENDING`、`OBSERVING`、`SUCCEEDED`、`FAILED`、`UNKNOWN`。
- `command_id`：同一批次的步骤记录相同批量命令 ID。
- `observed_status`：最终观察到的 `RUNNING` 或 `STOPPED`。
- `failure_message`：明确失败或未确认原因。

任务抽屉展示：

- 下发前即可看到本阶段全部 APP 行。
- 代理未返回时显示“等待运维代理返回执行结果”。
- 代理返回后、状态尚未收敛时显示“正在确认 APP 实际状态”。
- 使用不确定进度条，不生成虚假百分比。
- `FAILED` 使用错误色；`UNKNOWN` 和 `OBSERVING` 使用警告色。
- 表格保持最多十行的固定显示区，更多行在表格内部滚动。
- 所有新增文案覆盖中文、英文、日文和韩文。

## 7. 兼容与发布

旧代理的批量实现会直接返回成功但不执行 APP，中心不能先于代理启用批量传输。

中心使用 `KF_REDUNDANCY_BATCH_APP_COMMANDS` 控制冗余 APP 阶段：

- 缺失或 `false`：沿用现有单 APP 命令，仍通过统一网关结果模型更新任务。
- `true`：每个 APP 阶段下发一条批量命令。

发布顺序：

1. 中心保持开关关闭。
2. 升级两个冗余节点的运维代理。
3. 验证代理单 APP 命令及一条受控批量命令。
4. 升级中心和前端。
5. 开启开关并重启中心。
6. 验证首次生效、A→B 切换和 B→A 切换。

出现协议问题时关闭开关并重启中心即可回退，无需数据库回滚。

## 8. 验收标准

- 首次生效和普通切换各只产生一条 STOP 批量命令和一条 START 批量命令。
- 角色同步阶段产生零条 APP 命令。
- START 同时执行数不超过 4，STOP 同时执行数不超过 8。
- 代理不执行未列入本阶段的 APP，结果顺序与输入一致。
- Guard 任一项失败时整批实际执行数为 0。
- 中心保存失败批次的全部逐 APP 结果。
- 中心以实际 APP 状态决定步骤成功，不只相信命令返回。
- STOP 失败不改变原角色；START 失败保留新角色。
- 强制切换的离线源节点仍按既有规则跳过。
- 任务抽屉准确显示等待、确认、成功、失败和未确认状态。
- 普通 APP 管理相关代码没有修改。
- 无 SQLite 迁移、无 `.db` 文件、无新增 npm 依赖。
