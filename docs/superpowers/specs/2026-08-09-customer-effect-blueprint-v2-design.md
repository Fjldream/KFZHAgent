# 客户效果蓝图设计（内部契约 `DesignPlan v2`）

日期：2026-08-09  
状态：待用户复核

## 1. 背景与问题

当前设计确认阶段使用 `kf-design-plan/v1`。它只描述工程名、摘要、布局、风格、分区、控件类型和记忆点，适合内部粗规划，但不足以让客户确认最终效果。

真实回归中，客户在 v1 后提出“增加我的产品、丰富项目经历并用模拟数据占位”，模型生成的 v2 仅将项目经历区的 `text` 占位从 3 个增加到 6 个。工程名、摘要、布局、风格和记忆点均未改变，也没有新增产品区。前端只显示控件类型，客户无法知道需求是否真正落地。

问题来自三个层面：

1. 数据契约表达力不足，无法结构化承载页面目标、模块内容、示例数据、交互、修订差异和验收标准。
2. 模型提示词只要求“在上一版基础上修订”，没有强制逐条落实客户意见，也没有实质差异门禁。
3. 客户展示层把计划压缩成控件类型列表，隐藏了内容意图和修改结果。

## 2. 目标与非目标

### 2.1 目标

- 客户在批准前能完整理解工程最终会呈现什么内容、效果和交互。
- 从第一次生成方案开始，每一版客户方案都使用完整的效果蓝图结构，不能首版简略、修订版才详细。
- 每条新增或修改意见都能映射到具体页面或模块。
- 修订版明确展示相较上一版“新增、调整、保留”的内容。
- 内容型工程可以提供真实感较强的模拟数据，避免空白占位。
- 只有客户明确确认效果蓝图后，系统才生成工程变更计划。
- 历史 `DesignPlan v1` checkpoint 可以恢复并继续修订。

### 2.2 非目标

- 客户效果蓝图不展示 KF GUID、坐标、变量 ID、底层 JSON 或内部工具调用。
- 本次不改变工程生成、构建、部署和下载机制。
- 本次不引入自由 JavaScript 或超出当前受控 DSL 的交互。
- 本次不要求实现折叠的“工程技术蓝图”。

## 3. 方案选择

采用新增 `kf-design-plan/v2` 并兼容读取 v1 的方案。

不直接修改 v1，是因为历史 checkpoint 中已持久化严格的 v1 数据。新建或修订蓝图统一输出 v2；读取历史状态时接受 v1；当用户修订历史 v1 时，模型以 v1 为输入并产出完整 v2，从而完成自然升级。

这里的 `v2` 只表示内部数据契约升级，不代表“客户第二次收到的方案”。系统分开维护两个版本概念：

- 内部契约版本：`schema: "kf-design-plan/v2"`，仅供系统校验、存储和程序处理，客户界面不展示。
- 客户修订版本：`效果蓝图 v1`、`效果蓝图 v2`、`效果蓝图 v3`，表示同一方案在对话中的历次修订。

因此，新客户第一次收到的就是完整详细的“效果蓝图 v1”；客户补充需求后收到同样完整、并突出差异的“效果蓝图 v2”。不存在先给简略方案、第二版才给详细方案的路径。

## 4. 客户效果蓝图内部契约

`DesignPlan v2` 至少包含以下信息：

```ts
interface CustomerEffectBlueprintV2 {
  schema: "kf-design-plan/v2";
  displayName: string;
  overview: {
    objective: string;
    audiences: string[];
    scenarios: string[];
    valueProposition: string;
  };
  informationArchitecture: {
    narrative: string;
    wireframe: string;
  };
  modules: Array<{
    id: string;
    name: string;
    purpose: string;
    content: string[];
    sampleData: Array<{
      label: string;
      value: string;
    }>;
    interactions: string[];
    presentation: string;
  }>;
  visualDirection: {
    tone: string;
    colors: string[];
    typography: string;
    spacingAndSurfaces: string;
  };
  highlights: string[];
  revisionNotes: {
    added: string[];
    changed: string[];
    retained: string[];
  };
  acceptanceCriteria: string[];
  openQuestions: string[];
}
```

字段约束：

- `modules` 必须至少包含一个模块，每个模块必须说明用途和具体内容。
- 用户要求“内容充实”或允许模拟数据时，相关模块的 `sampleData` 不得为空。
- `revisionNotes` 在首次生成时可将主要设计决策放入 `added`，`changed` 和 `retained` 可为空；修订时必须反映相对上一版的真实变化。
- `acceptanceCriteria` 必须是客户可以观察或验证的结果，不能写内部实现任务。
- `openQuestions` 只记录不妨碍当前蓝图生成、但值得后续确认的信息。
- 所有数组设置合理上限，防止模型输出失控；文本字段设置长度上限，保证 checkpoint 与消息体有界。

## 5. 模型生成与修订流程

### 5.1 首次生成

模型接收最近会话、累计需求和澄清答案，直接生成完整详细的效果蓝图。其内部结构为 `kf-design-plan/v2`，客户标题显示“效果蓝图 v1”。提示词要求使用面向客户的专业顾问语言，内容具体、可执行，但不出现内部工程术语。

### 5.2 修订生成

修订输入包含：

- 上一版完整蓝图；
- 最近会话和客户最新意见；
- 从最新意见提取的逐条约束；
- 明确的“保留未被修改内容”要求。

模型必须逐条完成以下映射：

1. 客户意见对应哪个页面或模块。
2. 需要新增、调整还是保留什么内容。
3. 客户最终能够观察到什么变化。
4. 该变化进入 `revisionNotes` 和 `acceptanceCriteria` 的哪一项。

### 5.3 实质差异门禁

不能再用“版本号变化”代替“方案变化”。修订产物进入展示前进行确定性检查：

- 去除 `revisionNotes` 后，对上一版与新版主体进行规范化比较；主体完全相同则拒绝。
- 最新意见中的关键名词必须能在模块名称、模块内容、示例数据、交互或验收标准中找到可解释的落点。
- `revisionNotes.added` 与 `revisionNotes.changed` 在修订时不能同时为空。
- `revisionNotes` 声明的变化必须能在新版主体中找到对应内容。

若门禁失败，模型在同一回合内携带失败原因重试一次。第二次仍失败时，不向客户展示伪修订版；对话回到 `design-review`，给出明确、可继续沟通的错误提示，并保留上一版有效蓝图。

## 6. 客户可见展示

对话中的蓝图卡片按客户阅读顺序展示：

1. 标题、版本和一句定位。
2. “方案要点”或“本次更新”——首次生成展示主要设计决策；修订版优先展示新增、调整和保留项。
3. 方案目标——目标受众、使用场景和核心价值。
4. 整体结构——布局说明和 ASCII 线框。
5. 页面模块——用途、具体内容、示例数据、交互和表现方式。
6. 视觉方向与方案亮点。
7. 最终验收效果。
8. 待确认事项。
9. “确认蓝图”和“继续修改”引导。

前端继续使用 Vue 模板插值，不使用 `v-html`，模型文本必须保持转义。旧契约消息仍按现有卡片展示；新契约使用新的结构化卡片。客户界面只显示修订版本，不显示契约版本。消息的持久化格式应从脆弱的行文本解析升级为带明确边界的版本化载荷，展示层无法识别时安全回退为纯文本。

## 7. 对话状态与批准规则

- 每次生成完整效果蓝图后，状态保持 `design-review`。
- 客户补充模块、内容、交互、风格或数据要求时，意图归一化为 `REVISE_DESIGN`。
- 客户明确回复“确认”“按这个蓝图生成”等，才归一化为 `CONFIRM_DESIGN`。
- `CONFIRM_DESIGN` 后将已确认的 v2 蓝图交给 ChangePlan 生成器；工程计划必须引用蓝图模块和验收标准。
- 修订失败不得清除上一版蓝图，也不得进入 ChangePlan 审批。

## 8. 向后兼容

- 状态契约接受 v1 或 v2，历史 checkpoint 无需数据迁移。
- 新建蓝图从客户可见的第一版开始就产出完整的新契约结构。
- 历史 v1 在下一次修订时升级为 v2。
- 已经确认的 v1 仍可沿用原 ChangePlan 路径，避免阻断现有会话。
- 前端 `parseDesignPlan` 保留 v1 解析，新 v2 使用独立解析器或版本化消息载荷。

## 9. 错误处理

- 模型输出不符合 v2 schema：拒绝落库、保留上一版、返回可理解提示。
- 修订无实质变化：触发一次定向重试；仍无变化则提示客户重新描述或补充细节。
- 客户要求超出当前 KF 能力：蓝图中不得承诺无法生成的功能，应标记为待确认或降级方案。
- 示例数据不得包含真实个人敏感信息；默认使用明显为模拟但内容完整的数据。
- 客户确认时继续校验当前 `designPlanHash`，防止确认旧版本。

## 10. 测试策略

### 10.1 契约测试

- 新内部契约的完整对象通过校验。
- 缺少模块用途、内容、验收标准或修订信息时失败。
- v1 与 v2 均能被状态恢复读取。

### 10.2 模型端测试

- 提示词包含客户语言、模块详情、示例数据、修订差异和验收标准要求。
- 修订输入包含上一版蓝图和客户最新意见。
- 个人简历案例中，“新增产品、丰富项目、允许模拟数据”必须形成独立产品模块、完整项目示例和可观察验收项。

### 10.3 编排测试

- 首次生成进入 `design-review` 并保存 v2。
- 有效修订增加版本且主体发生变化。
- 完全相同的修订被拒绝，旧蓝图保持不变。
- 修订失败不创建 ChangeRequest、ChangePlan 或 BuildJob。
- 明确确认后才进入工程计划审批。

### 10.4 前端测试

- 客户可见的每一版卡片都展示目标、模块、示例数据、交互和验收标准；修订版额外突出本次更新。
- v1 历史消息仍可正常显示。
- 模型文本被安全转义。
- 长内容可读、可滚动，移动端不溢出。

### 10.5 真实模型回归

使用 DeepSeek 执行固定回归对话：

1. “个人简历网站”。
2. “① 求职应聘”。
3. “我希望有我的产品、项目经历，可以使用假的数据占位，但是内容要充实”。

验收：首次方案必须已经是完整详细的客户效果蓝图；客户补充需求后的下一修订版必须新增独立产品模块；项目模块包含背景、职责、方案和成果示例；“本次更新”逐条说明变化；不得只增加控件数量。

## 11. 实施边界

本次实施覆盖 contracts、DeepSeek ModelPort、Agent Orchestrator、消息格式化/持久化与 Web 蓝图卡片。工程 JSON 生成器和领域工具不在本次重构范围内，但 ChangePlan 生成提示词需要能消费 v2 蓝图，确保后续工程计划不会丢失已确认的客户效果要求。
